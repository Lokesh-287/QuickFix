# QuickFix – Multi-Site Configuration

## Configuration Files Explanation

`site_config.json` stores configuration specific to a single site such as database credentials, developer mode, and site-level secrets.
`common_site_config.json` stores bench-wide shared settings applied to all sites in the same Frappe bench.
If a secret (like database password or API key) is accidentally placed in `common_site_config.json`, every site gains access to it, causing security leakage across tenants.
This breaks isolation in Frappe's multi-tenancy model and can expose confidential production data.

## Bench Processes

Running `bench start` launches four main processes:

* **web** – handles HTTP requests and serves the Frappe application.
* **worker** – executes background jobs from Redis queues.
* **scheduler** – triggers scheduled tasks such as emails and periodic jobs.
* **socketio** – manages realtime updates and notifications.

If the worker process crashes, background jobs remain queued in Redis but will not execute until the worker restarts, causing delayed emails, reports.

## Request 3: `/track-job`

When a browser hits `/track-job`, Frappe treats it as a website route instead of an API request. The framework’s website router searches for a matching file inside the app’s `www/` directory. If `quickfix/www/track-job.html` or `quickfix/www/track-job.py` exists, Frappe automatically maps the URL to that file. If a Python file is present, its `get_context()` function prepares data which is then rendered using the HTML template and returned as a web page response.

## Step 2 — Session & CSRF

When inspecting a POST request in browser Developer Tools, the request headers include `X-Frappe-CSRF-Token`. This token is generated by Frappe during user login and is associated with the active session identified by the `sid` cookie. The frontend automatically sends this token with every POST request so the server can verify that the request originates from the authenticated user’s browser. If the CSRF token is omitted or invalid, Frappe rejects the request with a permission error (HTTP 403), preventing Cross-Site Request Forgery attacks.

In bench console, running `import frappe; frappe.session.data` shows the session data available in the current execution context. Since bench console is not an HTTP request environment, no browser session is loaded and the session data is typically empty (`{}`), indicating that no authenticated web session is active.

## Step 3 — Error Visibility ( I have tested this but still getting  traceback )

With `developer_mode: 1`, triggering a Python exception inside a whitelisted method returns a full traceback in the browser. The response includes the exception type, file name, line number, and stack trace, which helps developers debug issues during development.

After setting `developer_mode: 0` and repeating the same request, the browser only receives a generic *Server Error* message. The detailed traceback is hidden from the client. This is important for production environments because exposing internal errors could reveal sensitive implementation details and create security risks.

Even though errors are hidden from the browser in production, they are still recorded internally. Production errors can also be viewed from the **Error Log** DocType inside the Frappe Desk interface.
